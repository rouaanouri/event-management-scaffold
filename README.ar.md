# نظام إدارة الفعاليات (Event Management Platform)

تطبيق ويب لإدارة الفعاليات مبني بـ React وTypeScript، يتصل بواجهة برمجة تطبيقات (API) حقيقية موزَّعة على بيئة استضافة خارجية. يوفّر التطبيق تجربتين منفصلتين: تجربة للمستخدم العادي (تصفح الفعاليات القادمة والتسجيل بها ومتابعة حالة التسجيل)، وتجربة للإدارة (إدارة كاملة للفعاليات والمسجلين).

## الحزمة التقنية

| الطبقة | الأداة |
|---|---|
| إطار العمل | React 19 + TypeScript |
| أداة البناء | Vite |
| التنسيق | Tailwind CSS v4 |
| إدارة الحالة | Zustand (مع `persist` middleware لحفظ الجلسة) |
| جلب البيانات والكاش | TanStack Query (React Query) |
| الاتصال بالـ API | Axios |
| التوجيه | React Router |
| الأيقونات | lucide-react |
| الخط | Cairo (عربي، عبر Google Fonts) |

## Setup Instructions

**المتطلبات الأساسية:** Node.js إصدار 18 أو أحدث، وnpm.

```bash
npm install
```

هذا الأمر يثبّت كل الحزم المذكورة أعلاه، بما فيها التبعيات التطويرية (TypeScript، oxlint).

## API Configuration

يعتمد المشروع على متغير بيئة واحد إلزامي:

```
VITE_API_URL=https://events-management-api-847aeb3c849e.hosted.ghaymah.systems
```

يُنسخ ملف `.env.example` إلى ملف باسم `.env` بجذر المشروع (القيمة الافتراضية بالملف تشير مسبقاً إلى عنوان الـ API المعتمد في هذا المشروع؛ لا حاجة لتعديلها إلا عند الاختبار مقابل بيئة مختلفة).

```bash
cp .env.example .env
```

> ملاحظة: بادئة المتغير هي `VITE_` وليست `NEXT_PUBLIC_` (الواردة كمثال توضيحي في وصف المهمة)، لأن هذا المشروع مبني بـ Vite لا Next.js. أي متغير بيئة يُراد كشفه للكود الأمامي في مشروع Vite يجب أن يبدأ بالبادئة `VITE_` تحديداً، وإلا لن يكون متاحاً في الكود المصرَّف.

## Application Startup

```bash
npm run dev
```

يشغّل الأمر خادم تطوير محلياً (عادة على `http://localhost:5173`).

**حساب إدارة جاهز للاستخدام** (مزروع مسبقاً في الـ API):

| الحقل | القيمة |
|---|---|
| البريد الإلكتروني | `admin@example.com` |
| كلمة المرور | `admin123` |

لإنشاء حساب مستخدم عادي، تُستخدم صفحة "إنشاء حساب جديد" من داخل التطبيق.

## بيانات اختبار (Seed Data)

نظراً لأن إنشاء الفعاليات محصور بحساب الإدارة عبر واجهة برمجية تتطلب مصادقة، أُرفق سكريبت مستقل لتعبئة الـ API الحقيقي ببيانات اختبار متنوعة (لا يُشحن كجزء من تطبيق الواجهة، أداة تطوير فقط):

```bash
node scripts/seed-events.mjs
```

يضيف السكريبت 15 فعالية موزّعة على الأنواع الثلاثة (مؤتمر، ندوة، ورشة عمل) وتواريخ متعددة، مفيدة لاختبار البحث والفلترة. السكريبت مُصمَّم بمقاومة لبطء الاستضافة (انظر قسم الافتراضات أدناه): مهلة 30 ثانية لكل طلب، وإعادة محاولة تلقائية حتى 4 مرات، ومتابعة العمل حتى لو فشلت إضافة فعالية واحدة بدلاً من إيقاف العملية بالكامل.

## Build & Deployment

```bash
npm run build
```

يُنتج بناءً جاهزاً للإنتاج في مجلد `dist/`، مقسَّماً تلقائياً إلى ملفات منفصلة لكل صفحة (code splitting عبر `React.lazy`) لتقليل حجم التحميل الأولي.

```bash
npm run preview
```

يُشغّل نسخة محلية من بناء الإنتاج للمعاينة قبل النشر الفعلي.

**النشر:** لم يُنشر المشروع بعد على منصة استضافة (Vercel/Netlify)، وهذا أحد البنود الاختيارية المتبقية.

## بنية المشروع

```
src/
├── api/            دوال الاتصال المباشر بكل مسار من مسارات الـ API
├── components/     مكوّنات واجهة قابلة لإعادة الاستخدام (منظَّمة حسب الوظيفة)
├── features/       صفحات التطبيق الكاملة (كل صفحة في مجلدها)
├── hooks/          خطافات React مخصَّصة (مثل useDebouncedValue)
├── lib/            أدوات مساعدة عامة (تحقق، أخطاء، JWT، إعداد الكاش)
├── routes/         مكوّنات التوجيه والحماية
├── stores/         حالة التطبيق العامة (Zustand)
└── types/          تعريفات TypeScript المشتركة
```

## Assumptions, Limitations and Trade-offs

هذا القسم يوثّق كل فجوة أو تعارض حقيقي اكتُشف بين وصف الـ API المكتوب (`API_DOCUMENTATION.md`) والسلوك الفعلي الموثَّق في مجموعة Postman المرفقة، والقرار المتَّخذ في كل حالة.

### 1. تسجيل الدخول لا يُعيد بيانات المستخدم

يُعيد `POST /auth/login` حقل `access_token` فقط، دون أي كائن `user`، ولا يوجد مسار مكافئ لـ `/auth/me` لجلب هوية المستخدم الحالي بعد تسجيل الدخول. الحل المعتمَد: فكّ تشفير محتوى رمز JWT محلياً (decode لا verify) لاستخراج المعرّف والدور، على اعتبار أن التحقق الأمني الفعلي من الرمز يتم من جهة الخادم مع كل طلب لاحق أصلاً؛ القيم المستخرجة محلياً تُستخدم فقط لأغراض عرض الواجهة (مثل إظهار رابط لوحة الإدارة).

### 2. تعارض تسمية الحقول بين التوثيق والاستجابة الفعلية

يصف `API_DOCUMENTATION.md` استجابة `POST /auth/register` بصيغة `camelCase` (مثل `firstName`)، بينما تُظهر الاستجابة الفعلية المسجَّلة في Postman صيغة `snake_case` (`first_name`, `last_name`, `date_of_birth`, `created_at`). اعتُمدت الاستجابة الفعلية مصدراً للحقيقة، لأنها نتيجة استدعاء حقيقي موثَّق وليست وصفاً نظرياً.

### 3. اختلاف اسم مفتاح القائمة المُرقَّمة بين المسارات

تُعيد `GET /events` و`GET /events/upcoming` عناصر القائمة تحت مفتاح `items`، بينما يُعيد `GET /registrations/event/{eventId}` نفس بنية الترقيم لكن تحت مفتاح `attendees`. عولجت هذه الفروقات عبر تعريف أنواع TypeScript مستقلة لكل حالة بدلاً من افتراض بنية موحَّدة قسرية.

### 4. `PATCH /events/{id}` موثَّق نظرياً لكنه غائب عملياً

يصف التوثيق النصي مساراً لتعديل فعالية قائمة (`PATCH /events/{id}`)، لكنه غير موجود إطلاقاً في مجموعة Postman المرفقة. لم يُنفَّذ هذا المسار في التطبيق، لأنه ليس من المتطلبات الوظيفية الأساسية المطلوبة أصلاً (المطلوب: إنشاء وحذف فقط)، وتعذَّر التحقق من شكله الفعلي.

### 5. بيانات المسجِّل بلوحة الإدارة محدودة

يحتوي كائن `user` المرفق مع كل تسجيل في `GET /registrations/event/{eventId}` على `id` و`email` و`role` فقط، دون اسم المستخدم الكامل. لذلك تعرض لوحة الإدارة البريد الإلكتروني للمسجِّل بدلاً من اسمه، وهذا قيد فرضته بنية الـ API لا خيار تصميمي.

### 6. اكتشاف "الفعالية مكتملة العدد" محدود بصفحة التفاصيل

حقل `registrationCount` غير موجود في استجابة `GET /events/upcoming` (قائمة الفعاليات)، بل في `GET /events/{id}` فقط (تفاصيل فعالية واحدة). نتيجة لذلك، لا يمكن تمييز الفعاليات المكتملة العدد بصرياً في قائمة البطاقات، بل فقط بعد فتح صفحة التفاصيل الخاصة بها.

### 7. بطء واستضافة الـ API

الخادم المستضاف عرضة لحالات سكون (cold start) تؤدي أحياناً إلى مهلات اتصال تتجاوز 10 ثوانٍ عند أول طلب بعد فترة خمول. عولجت هذه المشكلة على مستوى الواجهة الأمامية عبر ثلاثة إجراءات مكمِّلة لبعضها:
- طلب "إيقاظ" خفيف يُرسَل فور تحميل التطبيق، قبل أي تفاعل من المستخدم.
- إعادة محاولة تلقائية واحدة لأي طلب قراءة (GET) يفشل بسبب خطأ اتصال.
- كاش عبر TanStack Query بمدة صلاحية 5 دقائق، لتقليل عدد الطلبات الفعلية للسيرفر عند التنقل المتكرر بين الصفحات. كل عملية تغيير بيانات (إنشاء، حذف، موافقة، تسجيل) تُبطِل الكاش المرتبط بها فوراً ويدوياً، فلا تتأثر حداثة البيانات بعد أي إجراء يقوم به المستخدم نفسه.

هذه الإجراءات تخفّف الأثر لكنها لا تلغيه بالكامل؛ الحل الجذري يتطلب استضافة أفضل، وهو خارج نطاق هذا المشروع.

### 8. أداة فحص الكود (Linter)

المشروع مزوَّد بـ oxlint فقط (الإعداد الافتراضي القادم من قالب Vite الحديث). لم يُضَف ESLint فوقه، قرار واعٍ اتُّخذ بسبب ضيق الوقت المتاح للتسليم، مع العلم أن oxlint وESLint ليسا بديلين متكافئين بالكامل (ESLint أنضج في قواعد الوصولية وTypeScript المتقدمة).
